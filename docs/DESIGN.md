# KESELA 設計書（v1.10.0）

開発指示書 v1.0 の「最初のタスク」への回答。

**v0.2〜v0.3 の変更点**
- 技術構成を React + TypeScript から **素の HTML / CSS / JavaScript（ビルドなし）** に変更（ユーザーが React/TS 未経験のため）
- 確認事項の回答を反映：端末は iPhone／カテゴリはマスタ化／価格は税込合計額＋数量／購入後の「在庫に反映」ボタンは不要
- 購入済み抑制は「在庫変更」または「見直し完了」ボタンで解除（Q5）
- 画面の自動更新は Dexie の liveQuery で実現
- Dexie は 4.4.6 を `vendor/` に同梱（npm 不要）

---

## 1. 要件の理解と整理

### アプリの本質
「いつも買うもの」が決まっている人のための、**在庫 → 買い物リスト → 買う → 価格を記録** のループを最小の操作で回すアプリ。健康提案はその横に置く補助機能。

### 機能の骨格

| 領域 | 中心となる操作 | 肝になるロジック |
|---|---|---|
| 在庫 | 現在庫を ± で変える | なし（手動のみ。自動増減しない） |
| 買い物リスト | 「更新」ボタン／チェックで購入済み | 不足計算・重複防止・購入済みの再追加抑制 |
| 店舗・価格 | 店舗登録、売り場順、価格入力 | 店舗ごとの最新価格・単位価格換算・最安判定 |
| 健康提案 | 悩みを選ぶ → 食材をリストへ | 静的データの表示のみ |
| 設定 | バックアップ書き出し／復元／初期化 | JSON検証・データバージョン |

### 明示的に「やらないこと」（初期版）
- 購入による在庫の自動増減、内容量ベースの在庫計算
- 手動追加品の商品マスタ登録
- リアルタイム価格取得、レシートOCR、クラウド同期、複数端末
- 健康提案からの自動追加、自由入力による相談

## 2. 推奨技術構成

**方針：ビルド不要の素の HTML / CSS / JavaScript。** ファイルをそのまま置けば動く。npm やビルドの知識は不要。

| 用途 | 採用 | 理由 |
|---|---|---|
| 画面 | HTML 1枚 + JavaScript（ES Modules） | `import` / `export` でファイルを分割できる。ブラウザが標準で対応 |
| 画面遷移 | URL の `#` で切替（`#/list`, `#/stock` …） | ページ遷移なしでタブ切替。リロードしても同じ画面に戻る |
| DB | **Dexie.js**（1ファイルを `vendor/` に置く） | 生の IndexedDB は記述量が多くバグを生みやすい。npm 不要で使える |
| 画面更新 | Dexie の `liveQuery`（`js/ui/live.js` の `watch()`） | データが変わると関係する画面が**自動で**描き直される。React なしで自動更新を実現 |
| ホーム画面追加・オフライン | `manifest.webmanifest` + `sw.js`（自作・数十行） | **iPhone でのデータ保持に必須**（6章 A） |
| バックアップ検証 | 自作の検証関数 | 対象テーブルが少ないので外部ライブラリ不要 |
| テスト | Node.js 標準のテスト機能（`node --test`） | 追加インストール不要。計算ロジックだけ自動テストする |
| スタイル | 素の CSS（CSS 変数） | 指示書どおり |
| 公開先 | GitHub Pages（無料） | フォルダをアップするだけで HTTPS の URL になる。PWA には HTTPS が必須 |

### React/TS をやめることで変わること
- 得：学習コストゼロ、ビルド不要、Web 制作の知識でコードが読める
- 失：型チェックがないため、データの形の間違いに気づきにくい → 計算ロジックのテストと、関数冒頭のコメント（JSDoc）で補う

### 開発時の注意
ES Modules は HTML ファイルをダブルクリック（`file://`）で開くと動かない。開発中は VS Code の拡張機能 **Live Server** などでローカルサーバーを立てて確認する。ホーム画面追加などの PWA 機能は HTTPS が必要なため、iPhone での最終確認は GitHub Pages 上で行う。

## 4. データベース設計

### 共通方針
- ID は `crypto.randomUUID()` の文字列。連番にしないことで、将来のクラウド統合時に ID が衝突しない。
- 日時は ISO 8601 文字列（`2026-10-30T19:00:00+09:00`）、購入日は `YYYY-MM-DD`。
- 金額は円の整数、税込（確認事項 Q3）。

指示書の HealthRecommendation はユーザーが編集しない固定データなので、`js/content/healthRecommendations.js` にコードとして持つ。バックアップ対象外になり、内容の更新もアプリ更新だけで済む。

### 買い物リスト更新のロジック（核心部分）

```
「リストを更新」押下時、商品ごとに:
  不足数 = 目標在庫 − 現在庫
  リストに既にある（productId一致）
      → 追加しない。数量を最新の不足数に更新する（不足数≦0なら「在庫充足」表示で残す）
  リストに無い
      → 不足数 > 0 かつ autoAddSuppressed = false なら追加
手動追加品・健康提案から追加した品には一切触れない
```

購入済み抑制（確定）：
- マスタ品を購入済みにする → リストから削除し、`autoAddSuppressed = true`
- 解除条件：在庫数・目標在庫の変更、**または在庫画面の「見直し完了」ボタン**で全商品の抑制を解除 → 続けてリスト更新
- この切り替えは `productRepo` の中だけで行い、画面側には書かせない（漏れ防止）

### 最安判定のロジック
1. 各店舗の最新記録（purchasedAt が最大、同日なら createdAt が最大）を取る
2. 1管理単位あたり価格 = price ÷ quantity
3. 全店舗の最新記録に同じ次元（g / ml / 個）の内容量があれば単位価格（100g・100ml・1個あたり）で比較
4. そうでなければ1管理単位あたり価格で比較し、「容量未登録のため1パックあたりで比較」と注記
5. 記録が古い（90日超を仮案）ものは日付を強調表示

## 6. 実装上の懸念点・仕様の矛盾

### A. 【重要】iPhone ではデータが自動で消える可能性がある
Safari は「7日間そのサイトを開かなかった場合、サイトのデータを削除する」仕様がある。ホーム画面に追加した Web アプリ（PWA）はこの対象外。
**対策**：PWA 化してホーム画面から使うことを前提にする／`navigator.storage.persist()` で保護を要求／設定画面に最終バックアップ日を表示し、一定期間あいたら促す。

### B. 「サーバー不要」と「スマホで使う」の関係
スマホのブラウザで開くには、どこかにファイルを置いて URL でアクセスする必要がある。静的ホスティング（ファイル置き場）は無料で、サーバー処理もしないので指示書の条件には反しないが、方針として決めておきたい。
なお IndexedDB は URL（ドメイン）ごとに別保存なので、**公開先を後で変えるとデータは引き継がれない**（バックアップ→復元で移行）。

### C. 【重要】「在庫が変わらない」と購入済み抑制が永遠に解除されない
運用は「買い物の前に在庫を見直す」（Q4 回答）。このとき次のケースで不具合になる：

1. 卵：アプリ上の在庫 0 / 目標 2 → リストに 2 パック
2. 買って「購入済み」→ 抑制 ON（アプリ上の在庫は 0 のまま）
3. 1週間で食べ切る。次の見直しで実物も 0 → アプリも 0 なので**変更しない**
4. 在庫が「変更」されていないので抑制が解除されず、**卵がリストに戻らない**

**提案**：在庫画面に「見直し完了」ボタンを置き、押すと全商品の抑制を解除してそのままリストを更新する。見直し後のワンタップで、そのとき実際に足りないものだけがリストに入る。（Q5）
あわせて、在庫画面では抑制中の商品に印を付ける。

### D. カテゴリが自由入力だと売り場順が成立しない
→ カテゴリをマスタ化（4章 categories）。（Q2）

### E. 売り場順は「カテゴリ単位」か「商品単位」か
指示書は両方に触れているが、データ設計はカテゴリ単位のみ。商品単位まで店舗ごとに並べるのは設定の手間が大きいので、**初期版はカテゴリ単位、同カテゴリ内は商品名順**を提案。一時項目はカテゴリ未設定なら末尾。

### F. 価格の定義があいまい
PriceRecord に price と quantity があるが、price が「1個の値段」か「合計額」か未定義。また税込/税抜も未定義。
**提案**：レシートの1行と同じ「税込の合計額＋数量」で記録し、1個あたりはアプリが計算（将来のOCRとも一致）。（Q3）

### G. 単位の混在
同じ牛乳でも「1L」「1000ml」と入力される可能性がある。保存時に g / ml / 個 へ正規化する。次元が違う（g と 個）記録同士は単位価格比較しない。

### H. 手動追加品・健康提案品には価格を記録できない
PriceRecord は productId 必須のため。初期版はそれで問題ないと考えるが、気に入った食材を後から商品マスタに登録する導線（「マスタに登録」ボタン）は将来検討。

### I. リストにある商品の在庫が変わった場合
重複追加はしないが、数量は最新の不足数に更新する（4章ロジック）。在庫が目標に達しても勝手には消さず「在庫充足」と表示する（「未購入は残す」との整合）。

### J. 健康提案の内容の正確さ
表示する栄養情報は一般的な内容に留め、文言は実装時にレビューしてもらう。断定的な効能表現（「治る」等）は使わない。

### K. 復元は「全置き換え」
マージ（合体）は ID 重複や整合性の問題が起きやすいため、復元は全データ置き換えとし、確認画面で現在のデータ件数とバックアップの件数を並べて表示する。

## 9. 実装で決めたこと（v1.0 / Phase 1〜6 完了時点）

### 買い物リスト
- 購入済みにすると「元に戻す」「価格を記録」付きの通知を6秒表示（誤タップ対策）
- 「今回は買わない（削除）」も購入済みと同じく自動追加を止める（すぐ次の更新で復活しないように）
- 手動追加で商品マスタと同じ名前を入れた場合は、その商品として追加（価格記録・購入済み抑制が効く）。マスタには登録しない
- 同じ名前の項目がリストにあれば追加しない
- リストにある商品の数量は「リストを更新」で最新の不足数にそろう。在庫が足りても項目は消さず「在庫は足りています」と表示
- 選んだお店は保存され、次回もその売り場順で表示
- バックアップが未保存、または最後の保存から14日以上たつと、リスト画面の上に催促を表示

### 在庫
- 在庫数は 0〜999 の整数。＋連打でもずれないよう、読み出しと書き込みを1トランザクションで処理
- 抑制中の商品には「購入済み・在庫未更新」と表示
- 一番下に「見直し完了 → 買い物リストを更新」ボタン
- 商品を削除すると、その商品のリスト項目と価格記録も削除（確認画面で件数を表示）

### 店舗・価格
- 価格は「税込の支払額（合計）＋買った数」で記録し、1個あたり・単位価格はアプリが計算
- 最安判定：店舗ごとの最新記録（購入日→登録日時の順）だけを使う。全店舗に同種の内容量があれば単位価格（100g・100ml・1個あたり）、なければ1管理単位あたりで比較。同額は両方とも最安
- 90日より古い価格は赤字で「古い価格です」と表示
- 価格記録は入力ミス修正のため個別に削除できる（確認あり）
- 価格入力の内容量は、同じ店舗の前回記録 → 商品マスタの内容量 の順で自動入力
- 店舗を削除すると、その店舗の売り場順と価格記録も削除（確認画面で件数を表示）

### 健康・食材提案
- 8つの悩み × 5〜6食材の固定データ（`js/content/healthRecommendations.js`）
- 食材ごとに「安い／ふつう」の価格帯、理由、手軽な食べ方を表示
- 「＋ リスト」で手動追加（カテゴリ名が一致すれば売り場も設定）。追加済みは「リストにあり」
- 免責文に、薬との飲み合わせ（例：ワルファリンと納豆）・アレルギー・妊娠中の注意を明記

### バックアップ・設定
- iPhone では共有シート（「"ファイル"に保存」）、それ以外ではダウンロードで保存
- 復元は全置き換え。確認画面で「今のデータ」と「バックアップ」の件数を並べ、先に今のデータを保存するボタンも置く
- 検証：JSON形式、アプリ名、版（新しすぎる版は拒否）、ID の有無と重複、各項目の型
- 版を上げる時は `js/domain/backupFormat.js` の MIGRATIONS に変換を追加する
- 初期化は2回確認。初期カテゴリに戻す。最終バックアップ日は残す
- カテゴリの追加・名前変更・並び順・削除（商品が使っているカテゴリは削除不可）

### 画面共通
- 画面を切り替えると、開いていたシートは閉じる（戻るジェスチャー対策）
- 画面ごとに新しい入れ物を作り、前の画面のタップ処理が残らないようにする

## 12. v1.1 追加機能：毎日の食事・栄養・食費（2026-11-04）

### 決めたこと（ユーザー回答）
- 栄養データ：文部科学省「日本食品標準成分表（八訂）増補2023年」（令和8年3月27日正誤反映版 Excel）を取り込み。パッケージの栄養成分表示の手入力も可

### データ（DB 版2・バックアップ版2）
products に追加：
- `consumption` { breakfast, lunch, dinner } … 朝・昼・晩に食べる量。単位は内容量の単位（g / ml / 個）、内容量が未登録なら管理単位（パック等）
- `gramsPerUnit` … 1個（1パック）の重さ g。個・パックで量を入れる商品の栄養計算に使う（g・ml は不要。ml は水と同じ重さとみなす）
- `nutrition` … { source:'mext', code, name, per100g } または { source:'label', basisGrams, per100g }。100gあたりの値を商品に保存（成分表ファイルが無くても計算できる）
- `stockUpdatedOn` … 在庫数を確定した日
- 在庫数 `currentStock` は小数（第2位まで）を許可
meta：`profile` { sex, age, activity, menstruation }。バックアップの `settings.profile` にも保存
既存データは DB の版2移行・バックアップの MIGRATIONS[2] で自動的に新しい形になる

### 在庫の自動減少（js/domain/consumption.js）
- 今日の在庫 = 確定した在庫 − 1日の減り × 確定日からの日数（0未満にならない）。毎日0時に1日分減る
- 1日の減り（管理単位）= 1日の量 ÷ 1パックの内容量（内容量がなければ1日の量そのまま）
- DB は毎日書き換えない。在庫を ± したり商品を保存した時に「今日の在庫」で確定し直す
- 不足数は切り上げ（目標2・今日1.4 → 1パック）。リスト更新・在庫表示・リストの「在庫は足りています」は今日の在庫で判定
- 在庫画面に「毎日 0.2パック・あと7日」、3日以内になくなる物の件数を表示

### 栄養（js/domain/nutrition.js, js/content/dri2025.js）
- 13項目：エネルギー、たんぱく質、脂質、炭水化物、食物繊維、食塩相当量、カルシウム、鉄、ビタミンA・D・B1・B2・C
- 成分表の列：ENERC_KCAL, PROT-, FAT-, CHOCDF-, FIB-, NACL_EQ, CA, FE, VITA_RAE, VITD, THIA, RIBF, VITC。Tr・(0) は0、「-」は不明（合計に入れず * を付ける）
- 目標：推定エネルギー必要量（±10%で適正）、たんぱく質 推奨量以上（エネルギー比20%超で多い）、脂質20〜30%・炭水化物50〜65%（エネルギーから g に換算）、食物繊維 目標量以上、食塩 目標量未満、ミネラル・ビタミン 推奨量（D は目安量）以上、カルシウム・A・D は耐容上限量超えで警告
- 月経ありの女性（18〜64歳）は鉄の値を切り替え。75歳以上の活動量「高い」は「ふつう」の値
- 値の出典：厚生労働省告示（令和6年11月22日 第339号で全部改正）と2つ以上の資料で照合
- 18歳未満・妊娠中・授乳中は対象外と明記

### 食費（js/domain/cost.js）
- 入力単位1つあたりの値段 = 各店舗の最新記録から最安（1パックの価格 ÷ その記録の内容量）
- 1日の食費 = Σ 1日の量 × 単価、1か月 = 30日分。朝・昼・晩ごとにも表示
- 価格記録がない物は「計算に入っていない物」として一覧表示

### 画面
- 下部タブ「健康」→「食事」（#/health は #/meals に読み替え）。「栄養・食費」と「食材の提案」を切り替え
- 栄養・食費：1日／朝／昼／晩の切替、栄養素ごとの量・目標・判定バー、食費、朝昼晩ごとの毎日食べる物一覧（タップで編集）
- 商品フォームに「毎日食べる量（朝・昼・晩）」「栄養データ（成分表検索／パッケージ表示）」「1個あたりの重さ」を追加
- 成分表検索：カタカナ・ひらがなを区別しない、普段の言い方を成分表の言い方に変換（ご飯→めし、卵→鶏卵 など）、よく食べる物を先頭に
- 設定に「栄養の目標（性別・年齢・活動量）」と出典表記
- 日付が変わってからアプリに戻ると画面を描き直す
